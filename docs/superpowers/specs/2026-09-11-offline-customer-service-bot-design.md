# 博客离线客服机器人设计

## 目标

为 `blog.858846.xyz` 的在线客服增加离线机器人接管能力。管理员客服后台在线时继续由管理员人工回复；管理员不在线、用户端显示客服离线时，用户消息入库后由 DeepSeek `deepseek-flash` 立即生成回复。

机器人只处理本站、文章、账号和站内功能使用问题，不作为开放领域聊天机器人。

## 接管规则

现有 `CustomerServiceHub` 中的管理员 WebSocket 连接状态是管理员在线状态的唯一事实来源：

- 至少存在一个有效管理员 WebSocket：管理员在线，不调用机器人。
- 不存在管理员 WebSocket：管理员离线，机器人可接管。
- 用户消息始终先正常写入 D1 并立即返回，机器人生成在 `waitUntil` 后台任务中执行。
- 调用模型前检查一次在线状态，写入机器人回复前再次检查。如果期间管理员上线，丢弃模型结果，不写入机器人消息。
- 同一条用户消息最多触发一次机器人回复。

管理员关闭网页、断网或 WebSocket 断开后，沿用现有连接关闭事件更新在线状态。管理员重新打开客服后台并建立 WebSocket 后，机器人立即停止接管。

## 架构与组件

### 在线状态查询

为 `CustomerServiceHub` 增加内部只读状态接口，返回当前是否存在管理员连接。客服 API 通过 Durable Object stub 查询，不依赖浏览器上报的布尔值，避免伪造在线状态。

### 机器人调度器

用户端 `POST /api/customer-service/messages` 成功插入访客消息后，通过 `ctx.waitUntil` 调度机器人任务。任务接收会话 ID 和触发消息 ID，不接收未经规范化的请求对象。

调度器负责：

1. 验证该消息确实属于会话且发送方为访客。
2. 检查管理员当前离线。
3. 检查该消息尚未产生机器人回复。
4. 读取有限的最近会话上下文。
5. 调用 DeepSeek。
6. 再次检查管理员仍离线。
7. 以幂等方式写入机器人回复并通过现有 WebSocket 广播。

### DeepSeek 客户端

使用 OpenAI 兼容的 Chat Completions 接口：

- Base URL：`https://api.deepseek.com`
- Endpoint：`/chat/completions`
- Model：`deepseek-flash`
- Thinking：`disabled`
- Stream：`false`

独立配置名称：

- `CUSTOMER_SERVICE_AI_BASE_URL`
- `CUSTOMER_SERVICE_AI_ENDPOINT`
- `CUSTOMER_SERVICE_AI_MODEL`
- Secret：`CUSTOMER_SERVICE_AI_API_KEY`

客服机器人不得读取或复用主站的 `AI_MATCH_API_KEY`。

## 提示词与知识边界

系统提示词明确机器人身份为“Rowan Notes 客服机器人”，只能回答：

- 本站页面和导航位置；
- 文章浏览、搜索、收藏和评论；
- 注册、登录、账户资料和密码修改；
- 投稿、审核状态和我的文章；
- 在线客服、通知及其他已存在的站内功能。

对于无法由公开信息确认的问题、管理员专属操作、账户敏感数据、站外一般知识或与本站无关的问题，机器人不得编造答案，应说明其服务范围并提示用户等待管理员。

模型上下文包含固定的本站功能摘要，以及当前会话最近 12 条文本消息。单条消息继续遵守现有 2000 字符限制；发给模型的历史总长度设置上限，超出时从最早消息开始截断。

任何 Cookie、会话令牌、密码、API Key、邮箱验证码或服务端环境变量都不得进入模型上下文。

## 消息模型与界面

沿用 `blog_chat_messages` 表，不新增消息内容类型。机器人回复写为 `sender_type = 'admin'`，并使用稳定的机器人发送者 ID；客户端和后台根据该 ID 显示“客服机器人”，人工消息继续显示“客服”。

机器人回复使用确定性的 `client_message_id`，由触发用户消息 ID 派生，并利用现有唯一约束保证幂等。无需新增数据库迁移。

用户端保持现有气泡布局和主题颜色。离线状态文案补充“当前由客服机器人即时回复”；管理员在线时恢复现有人工客服文案。机器人气泡显示轻量身份标记，电脑端和手机端均不得挤压正文。

管理员后台能够查看机器人回复，但机器人回复不产生“客服回复”账户通知，避免用户同时收到实时气泡和重复站内通知。

## 失败处理

- DeepSeek 未配置、401/403、欠费、超时、限流、返回空内容或格式异常：用户消息仍保持发送成功。
- 模型失败时写入一条固定的机器人服务异常回复：“客服机器人暂时无法回复，管理员上线后会继续处理。”同一触发消息只写一次。
- 服务端日志只记录状态码、错误类别和请求阶段，不记录 Key、完整用户消息或模型完整返回。
- 管理员在线状态查询失败时按“管理员在线”处理，不启动机器人，优先避免错误抢答。

## 并发与幂等

每条访客消息对应唯一机器人回复 ID。插入前查询和数据库唯一约束共同防止刷新、网络重试、WebSocket 重连以及重复后台任务产生多条回复。

若用户连续发送多条消息，每条消息可分别触发任务；模型读取最新上下文。写入前若已经存在针对更新消息的机器人回复，仍允许当前消息对应的独立回复，但不得重复回复同一消息。

## 测试与验收

自动化测试覆盖：

1. 管理员在线时访客消息入库，但 DeepSeek 不被调用。
2. 管理员离线时访客消息立即返回，后台生成一条机器人回复。
3. 机器人生成过程中管理员上线，结果被取消。
4. 相同访客消息重复提交或任务重试，只存在一条机器人回复。
5. DeepSeek 失败时写入一次固定异常回复，不影响访客原消息。
6. 模型请求使用独立 Secret、`deepseek-flash` 和关闭思考模式参数。
7. 机器人拒绝回答与本站无关的问题，不虚构账户或管理员信息。
8. 用户端与管理员后台均正确显示“客服机器人”，深浅色主题和移动端布局正常。

生产验收使用两个独立浏览器会话：管理员后台未打开时验证机器人即时回复；后台打开并建立实时连接后验证机器人停止、人工回复正常。最终检查 D1 中无重复机器人消息，并确认日志未包含敏感信息。

## 不在本次范围

- 开放领域问答；
- 附件或图片识别；
- 知识库向量检索；
- 多机器人角色；
- 自动转人工工单分配；
- Cloudflare Queue。
