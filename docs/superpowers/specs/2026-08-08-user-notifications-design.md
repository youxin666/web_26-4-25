# Rowan Notes 用户站内消息中心设计

日期：2026-08-08

## 目标

为每位登录用户提供独立的站内消息中心，让用户及时获知与自己直接相关的评论、投稿审核和客服回复。消息中心需要在手机与桌面端保持现有 Rowan Notes 设计语言，完整适配中文、英文、浅色和深色模式。

第一版不引入邮件、推送通知、定时任务或 R2 存储，避免增加运维成本和免费额度消耗。

## 第一版消息类型

1. `comment_reply`：其他用户回复了当前用户发表的评论。
2. `article_comment`：当前用户发布的文章收到了一条新评论。
3. `submission_approved`：当前用户的投稿审核通过并成功发布。
4. `submission_rejected`：当前用户的投稿审核未通过。
5. `customer_service_reply`：客服向当前用户的客服会话发送了新消息。

只为登录用户生成消息。访客评论仍可公开显示，但访客没有稳定的用户身份，因此不会收到站内消息。用户回复自己的评论时不生成回复通知。如果同一条评论同时满足“评论回复”和“文章新评论”，且接收人相同，只保留信息更明确的“评论回复”消息。

系统公告作为未来扩展类型预留，不在第一版制作群发后台。点赞、访问量、收藏次数和草稿提醒不纳入第一版，避免低价值通知淹没重要消息。

## 用户体验

### 顶栏入口

- 登录后，顶栏显示消息铃铛；未登录时不显示。
- 有未读消息时显示数字角标，超过 99 条显示 `99+`。
- 角标变化不改变按钮尺寸，也不造成顶栏跳动。
- 点击铃铛进入 `/notifications`。
- 用户账户菜单同时增加“消息中心”入口，便于手机端和键盘用户访问。

### 消息中心页面

- 页面展示未读数量和按时间倒序排列的消息列表。
- 未读消息使用轻微主题色底色和状态圆点；已读消息降低强调度但仍保持清晰。
- 每条消息包含类型图标、主文案、补充文案和时间。
- 点击消息先标记为已读，再跳转到对应文章评论、已发布文章、我的文章或客服窗口。
- 支持单条标记已读和“全部已读”。
- 空状态显示“暂无消息”，加载失败提供重试按钮。
- 中文、英文文案由前端根据消息类型和结构化数据生成，数据库不保存固定语言句子。

### 跳转规则

- 评论回复：跳到对应文章评论区域，并定位相关评论。
- 文章新评论：跳到对应文章评论区域。
- 审核通过：跳到正式发布的文章。
- 审核不通过：跳到“我的文章”的“未通过”列表。
- 客服回复：打开文章站内客服窗口并恢复相应会话；消息中心链接使用可识别的查询参数触发打开。

## 数据设计

新增 D1 表 `blog_notifications`：

- `id`：消息 UUID。
- `user_id`：接收用户，外键指向 `blog_users.id`。
- `event_key`：业务事件唯一键，用于幂等去重。
- `type`：消息类型。
- `payload_json`：仅保存生成多语言文案所需的结构化字段，例如操作者名称、文章标题、文章链接和评论 ID。
- `href`：经过服务端限制的站内相对链接。
- `read_at`：未读时为空，已读时为 ISO 时间。
- `created_at`：创建时间。

索引覆盖用户时间线、未读查询和事件唯一键。评论表新增可空的 `user_id`，用于把登录用户评论与账户关联；旧评论保持为空，不尝试猜测归属。

消息保留策略：

- 正常查询或创建消息时，异步清理超过 90 天的消息。
- 每位用户最多保留最近 500 条；超过部分按创建时间从旧到新删除。
- 所有内容均存入 D1，不使用 R2。

## 服务端接口

所有消息接口均要求有效登录会话，并只操作当前用户的数据。

- `GET /api/notifications?limit=50&cursor=...`：返回分页消息和未读总数。
- `POST /api/notifications/read`：请求体为 `{ "id": "..." }`，只标记当前用户的一条消息。
- `POST /api/notifications/read-all`：标记当前用户全部消息为已读。
- `GET /api/notifications/unread-count`：供顶栏轻量读取未读数量。

`/notifications` 页面本身需要登录。未登录访问时跳转到登录界面，并在登录后返回消息中心。

## 事件写入

消息创建封装为一个可复用、幂等的服务端函数。业务流程完成后再写消息，避免向用户展示尚未真正完成的结果。

- 评论提交成功后：记录评论作者的 `user_id`；如为回复，通知根评论作者；如文章来自用户投稿，通知文章作者。
- 投稿发布成功且 D1 状态已更新后：通知投稿作者审核通过。
- 投稿拒绝状态更新成功后：通知投稿作者审核不通过。
- 客服消息成功写入后：当发送者为管理员且会话绑定了 `user_id` 时，通知该用户。

每个事件使用稳定的 `event_key`，例如 `comment_reply:<comment-id>`、`submission_approved:<submission-id>`、`customer_service_reply:<message-id>`。接口重试、重复点击或网络重连不会生成重复消息。

## 安全与错误处理

- API 不接受客户端指定目标用户；接收者始终由服务端业务数据推导。
- 查询、已读操作始终附带 `user_id = 当前用户 ID` 条件。
- `payload_json` 作为普通文本解析并转义显示，不允许注入 HTML。
- `href` 只允许站内相对路径。
- 消息写入失败不回滚已经成功的评论、审核或客服回复；通过日志记录并允许业务事件重试时依靠 `event_key` 补写。
- 未读数量接口禁止缓存，防止不同用户之间出现缓存串读。

## 前端结构

- 在现有共享顶栏中增加消息入口和未读角标，不复制另一套导航组件。
- 新增消息页面控制器，负责分页、空状态、已读状态和跳转。
- 扩展现有 i18n 字典，系统界面和消息文案完整覆盖中英文。
- 新增样式使用现有主题变量，适配浅色、深色、手机安全区域和 `prefers-reduced-motion`。

## 测试与验收

自动化测试覆盖：

- 不同用户只能读取和更新自己的消息。
- 评论回复、文章新评论、审核通过、审核不通过和客服回复均能生成正确消息。
- 访客评论、自回复和重复事件不会生成错误或重复消息。
- 单条已读、全部已读、未读计数和分页正确。
- 90 天清理和每用户 500 条上限不影响其他用户。
- 中英文文案、浅色/深色模式和移动端布局正确。
- 原有评论回复、投稿审核和客服聊天测试继续通过。

部署前运行格式检查、类型/语法检查、全部测试和生产构建；应用 D1 迁移后部署 Worker。生产验证登录、顶栏角标、消息列表、已读操作以及五类事件。若关键验证失败，回滚 Worker 到部署前版本；数据库迁移采用向后兼容的新增表和可空字段，不删除现有数据。
